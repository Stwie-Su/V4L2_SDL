# 性能优化设计（先设计清楚，暂不实现）

当前 `v4l2_display` 是"最简版"：单线程、阻塞取帧、每一帧都解码显示。
本文把优化路线设计好——每个优化点写清：**问题 → 做法 → 预期效果 → 怎么验证**。
后续想动手时，每项都可以独立加进现有代码，互不冲突。

## 先定测量口径

做任何优化前后，都用同一套指标对比，否则数字没有意义：

| 指标 | 怎么测 |
|---|---|
| 帧率 FPS | 程序里每帧计数，每秒打印（现在 [stats] 行就是这个） |
| CPU 占用 | 读 /proc/self/stat 的 utime+stime，折算成单核百分比（已实现） |
| 帧周期 | 相邻两帧 DQBUF 的时间差（clock_gettime），看平均值和最大值 |
| 显示延迟 | "帧被驱动填好的时刻 → 送进显示的这一刻"，两者之差 |

## 优化 1：排队策略（直接决定延迟）

**问题**：现在的循环是"取一帧 → 处理完 → 再取下一帧"。相机出帧比处理快时，
没人取的帧在驱动缓冲里排队；DQBUF 永远从队头拿"最旧的帧"——
显示的画面会越来越滞后（看到的可能是 1 秒前的场景）。

**做法**（参考 lv_port_linux 项目的做法）：

- DQBUF 循环取，一直取到没有为止（没帧时报 EAGAIN）
- 中间取出来的旧帧直接 QBUF 还回，**不做任何处理**
- 只对"最后一帧"做解码和显示

**预期效果**：显示延迟降到 1 个帧周期以内；丢的是旧帧，观感"更跟手"。

**怎么验证**：处理速度人为放慢（比如解码后加 sleep 50ms）放大差异，
对比改动前后的延迟数字。

## 优化 2：解码器（影响 CPU 和帧率上限）

**问题**：stb_image 是单文件纯 C 库，方便但解码不快。

**做法**：换 libjpeg-turbo（带 SIMD 加速，x86 上会用到 SSE/AVX 指令）。

```bash
sudo apt install libjpeg-turbo8-dev    # 或 libjpeg-dev
```

**预期效果**：单帧解码时间明显下降（具体倍数实测为准）。

**怎么验证**：同一段 MJPG 数据，分别统计单帧平均解码耗时。

## 优化 3：多线程流水线（影响吞吐与卡顿）

**问题**：解码和显示串在取帧循环里，任何一步卡顿都会拖住取帧。

**做法**：拆成两个线程：

- 采集线程：只管 DQBUF / QBUF，把帧交给队列，马上回去取下一帧
- 处理线程：从队列取帧，解码 + 显示

队列用"环形缓冲 + 互斥锁 + 条件变量"，就是经典的生产者-消费者结构
（面试手撕高频题，这里正好有真实场景）。

**预期效果**：取帧不再被解码拖累；突发卡顿时丢帧而不是延迟累积。

**怎么验证**：处理线程故意睡 100ms，看采集侧帧率是否稳定不受影响。

## 优化 4：YUV 直传 GPU（进阶，进一步减 CPU）

**问题**：现在"JPEG 解码 → RGB 转换"整段都在 CPU 上做。

**做法**：libjpeg-turbo 直接解出 YUV420，交给 SDL 的 YUV 纹理
（`SDL_UpdateYUVTexture`），YUV→RGB 由 GPU 完成。

**预期效果**：CPU 明显下降（省掉转换、上传量也更小）。

**怎么验证**：同帧率下对比改动前后的 CPU 占用。

## 优化 5：等待方式（细节）

**问题**：阻塞式 DQBUF 睡眠等待，和窗口事件处理串在一起。

**做法**：改成 `poll()` 监听设备 fd + 非阻塞 DQBUF，事件驱动。
顺便这也是面试常问点（select/poll/epoll 的适用场景）。

**怎么验证**：对比 CPU 占用和每秒唤醒次数。

## 附：别忘了先测量再优化

本机相机实测（2026-10-15）：864×480 的实际能力上限 ≈ 5.8 fps，
当前程序已经跑满（5.7 vs 5.77）。也就是说**在这个相机上，
上面这些优化暂时看不出多大差别**——它们要在"更快的相机 / 更高分辨率 /
更高帧率"的场景下才有意义。

这正是"先测量、再优化"的活例子：不测就动手，可能优化了半天，
瓶颈其实在相机那头。
