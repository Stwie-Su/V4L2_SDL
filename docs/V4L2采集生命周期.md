# V4L2 采集生命周期（结合本程序）

> 本文按本程序的真实代码，讲一帧画面从“打开设备”到“关流释放”经过哪些阶段。
> 结构体字段细节见 [[V4L2结构体与能力树]]，这里重点讲**流程和状态变化**。

---

## 一、总览：三个阶段，九步 + 收尾

```text
配置阶段（只做一次）                      采集阶段（每帧循环）        结束阶段
─────────────────────────────────────    ─────────────────────    ─────────────────────
① open                                  ⑧ DQBUF                   STREAMOFF
② QUERYCAP                                 ↓                       munmap
③ S_FMT                                  使用 frame                 close
④ REQBUFS                                   ↓
⑤ QUERYBUF + mmap                        ⑨ QBUF
⑥ QBUF（全部入队）                           ↓
⑦ STREAMON                               回到 ⑧
```

对应到本程序的接口：

```c
v4l2_capture_start()   → ①～⑦
v4l2_capture_get()     → ⑧
v4l2_capture_done()    → ⑨
v4l2_capture_stop()    → 结束阶段
```

调用顺序：

```c
start → { get → done }* → stop
```

## 二、配置阶段：打开、协商、准备缓冲

全部封装在 `src/v4l2_capture.c:61` 的 `v4l2_capture_start()` 里。这个函数返回 0 时，驱动已经开始出帧。

### ① open：拿到设备 fd

```c
g.fd = open(dev, O_RDWR);
```

- `dev` 通常是 `/dev/video0`；
- 后续所有 ioctl 都用这个 fd；
- 本模块是单例：`g` 是文件内静态结构，一个进程只能有一路采集。

代码位置：`src/v4l2_capture.c:72`

### ② QUERYCAP：确认设备能干这活

```c
ioctl(g.fd, VIDIOC_QUERYCAP, &cap);

uint32_t caps = (cap.capabilities & V4L2_CAP_DEVICE_CAPS)
                ? cap.device_caps : cap.capabilities;

if (!(caps & V4L2_CAP_VIDEO_CAPTURE) ||
    !(caps & V4L2_CAP_STREAMING)) {
    /* 不是可流式采集设备 */
}
```

必须同时有：

- `V4L2_CAP_VIDEO_CAPTURE`：这是采集节点；
- `V4L2_CAP_STREAMING`：支持流式 I/O，能用 `REQBUFS/QBUF/DQBUF/STREAMON`。

有 `device_caps` 时优先用它，因为它描述的是**当前这个节点**的能力，而不是整个物理设备。

本机实测：`device_caps = 0x04200001`，采集和流式都有，但没有 `READWRITE`，所以不能用 `read()`。

代码位置：`src/v4l2_capture.c:79-91`

### ③ S_FMT：请求格式，并回读确认

```c
fmt.type          = V4L2_BUF_TYPE_VIDEO_CAPTURE;
fmt.fmt.pix.width = 1280;
fmt.fmt.pix.height = 720;
fmt.fmt.pix.pixelformat = V4L2_PIX_FMT_MJPEG;
fmt.fmt.pix.field = V4L2_FIELD_ANY;

ioctl(g.fd, VIDIOC_S_FMT, &fmt);
```

关键点：**驱动可以“讲价”**。你请求 1280×720 MJPG，驱动可能改成别的尺寸或格式。所以 `S_FMT` 之后一定要回读：

```c
if (fmt.fmt.pix.pixelformat != V4L2_PIX_FMT_MJPEG)
    /* 驱动没给 MJPG，直接失败 */
```

程序把驱动最终采用的尺寸存进 `g.width/g.height`，后面通过 `v4l2_capture_width()/height()` 查询。`main_display.c` 也用这个实际尺寸创建窗口和纹理，而不是盲目使用请求值。

代码位置：`src/v4l2_capture.c:94-114`

### ④ REQBUFS：向驱动申请缓冲

```c
req.count  = 4;
req.type   = V4L2_BUF_TYPE_VIDEO_CAPTURE;
req.memory = V4L2_MEMORY_MMAP;

ioctl(g.fd, VIDIOC_REQBUFS, &req);
```

含义：**我要 4 个 mmap 方式的缓冲**。

- 驱动可能不给足 4 个，`req.count` 会被改小；
- 程序要求至少 2 个，否则失败；
- 从这一步开始，缓冲正式存在，但还没有映射到用户空间。

代码位置：`src/v4l2_capture.c:117-130`

### ⑤ QUERYBUF + mmap：把内核缓冲映射进本进程

```c
for (i = 0; i < g.nbufs; i++) {
    struct v4l2_buffer buf = {0};
    buf.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
    buf.memory = V4L2_MEMORY_MMAP;
    buf.index = i;

    ioctl(g.fd, VIDIOC_QUERYBUF, &buf);

    g.length[i] = buf.length;
    g.addr[i] = mmap(NULL, buf.length,
                     PROT_READ | PROT_WRITE,
                     MAP_SHARED, g.fd, buf.m.offset);
}
```

- `QUERYBUF` 拿到每个缓冲的 `length` 和 `m.offset`；
- `mmap` 用这两个值把驱动缓冲映射到用户态；
- `MAP_SHARED` 必须保留：驱动写进去的数据，用户态才能看到；
- 映射成功后，用户直接读这块内存，没有额外拷贝。

代码位置：`src/v4l2_capture.c:133-151`

### ⑥ QBUF：把空缓冲交给驱动

```c
for (i = 0; i < g.nbufs; i++) {
    struct v4l2_buffer buf = {0};
    buf.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
    buf.memory = V4L2_MEMORY_MMAP;
    buf.index = i;
    ioctl(g.fd, VIDIOC_QBUF, &buf);
}
```

`QBUF` 的方向是“应用 → 驱动”：把空缓冲放进驱动的队列，驱动才有地方填帧。

为什么要在 `STREAMON` 之前全部入队？

- 驱动一开流就能立即写缓冲；
- 不会出现“已经开流但驱动手里没缓冲”的空窗；
- 4 个缓冲形成流水线，应用处理慢一点时也不至于立刻丢帧。

代码位置：`src/v4l2_capture.c:154-164`

### ⑦ STREAMON：正式开流

```c
enum v4l2_buf_type type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
ioctl(g.fd, VIDIOC_STREAMON, &type);
g.streaming = 1;
```

从这一刻起，驱动开始往已入队的缓冲里填帧。

注意：**STREAMON 返回成功 ≠ 第一帧已经好了**。第一帧要等驱动填完，应用调用 `DQBUF` 时才会阻塞等待。

代码位置：`src/v4l2_capture.c:167-171`

## 三、采集阶段：每帧的 DQBUF → 使用 → QBUF

### 帧循环

```c
while (还在取帧) {
    v4l2_capture_get(&frame, &len);   // ⑧ DQBUF

    /* 使用 frame[0..len) */

    v4l2_capture_done(frame);         // ⑨ QBUF
}
```

### ⑧ DQBUF：从驱动取一帧

```c
ioctl(g.fd, VIDIOC_DQBUF, &buf);
*frame = g.addr[buf.index];
*len   = buf.bytesused;
```

- `DQBUF` 是阻塞的：队列里没有满缓冲时，进程会睡在这里；
- 返回的 `buf.index` 告诉你“哪一块缓冲好了”；
- `buf.bytesused` 是这一帧的**实际字节数**，MJPG 就是 JPEG 数据的长度；
- 不要用 `fmt.fmt.pix.sizeimage` 当帧长：`sizeimage` 是缓冲上界，`bytesused` 才是本次真值。

代码位置：`src/v4l2_capture.c:181-199`

### ⑨ QBUF：用完还回去

```c
ioctl(g.fd, VIDIOC_QBUF, &buf);
```

`QBUF` 把这块缓冲重新交给驱动，驱动才能填下一帧。

本程序的 `v4l2_capture_done()` 用指针反查索引：

```c
for (i = 0; i < g.nbufs; i++) {
    if (g.addr[i] == frame) {
        index = i;
        break;
    }
}
```

所以必须把 `get` 给出的**原指针**传回来，不能传 `frame + 1`，也不能自己 `free`。

代码位置：`src/v4l2_capture.c:201-229`

### 缓冲的“所有权”状态机

```text
应用持有（可读） --QBUF--> 驱动队列（空，等待填充）
       ↑                              │
       │                              │ 驱动写满一帧
       │                              ▼
       └──────── DQBUF ──────── 完成队列（满，可读）
```

- `QBUF` 之后，应用**不应该再读写**这块内存；
- `DQBUF` 之后，这块内存归应用使用，直到再次 `QBUF`；
- 忘记 `QBUF`：驱动可用缓冲逐渐减少，4 个缓冲用完后，第 5 次 `DQBUF` 会永久阻塞；
- 重复 `QBUF` 同一帧：驱动会认为状态不对，返回错误。

### 本程序主循环

`src/main_display.c:127-164`：

```text
SDL 事件处理
    ↓
v4l2_capture_get()        // DQBUF，阻塞等帧
    ↓
stbi_load_from_memory()   // MJPG → RGB888
    ↓
v4l2_capture_done()       // 解码完立刻还缓冲
    ↓
SDL_UpdateTexture / RenderCopy / RenderPresent
    ↓
stats_tick()              // 每秒打印帧率和 CPU
```

一个细节：`done` 放在解码之后、SDL 上传之前。这样缓冲只被占用“解码所需的时间”，不会因为 SDL 渲染慢而长期占着驱动缓冲。

## 四、结束阶段：STREAMOFF → munmap → close

```c
void v4l2_capture_stop(void)
{
    if (g.fd < 0)
        return;

    if (g.streaming) {
        ioctl(g.fd, VIDIOC_STREAMOFF, &type);
        g.streaming = 0;
    }

    for (i = 0; i < g.nbufs; i++)
        munmap(g.addr[i], g.length[i]);

    close(g.fd);
    g.fd = -1;
}
```

顺序和原因：

1. **STREAMOFF**：先让驱动停止 DMA，不再往缓冲写数据；
2. **munmap**：解除用户态映射；
3. **close**：最后关闭 fd。

`stop` 是幂等的：`g.fd < 0` 时直接返回，重复调用安全。`start` 里任何一步失败都 `goto fail`，统一调用 `stop` 清理，所以不会出现“映射了一半、fd 还开着”的泄漏。

代码位置：`src/v4l2_capture.c:231-250`，失败路径在 `:176-178`。

## 五、失败路径也是生命周期的一部分

`v4l2_capture_start()` 的每一步失败都会跳到 `fail`：

```text
open 失败          → stop 直接返回
QUERYCAP 失败      → stop 关闭 fd
S_FMT 失败         → stop 关闭 fd
REQBUFS 失败       → stop 关闭 fd
QUERYBUF/mmap 失败 → stop 释放已映射的缓冲，再关闭 fd
QBUF 失败          → 同上
STREAMON 失败      → streaming 仍为 0，stop 跳过 STREAMOFF，直接 munmap + close
```

这就是为什么 `stop` 里要先判断 `g.streaming` 和 `g.addr[i]`：它要能处理“只完成了一半”的状态。

## 八、常见误区

1. **“STREAMON 一返回就有帧”**  
   错。STREAMON 只是启动采集，第一帧要等驱动填完，DQBUF 会阻塞。

2. **“frame 指针可以一直保存”**  
   错。它指向驱动缓冲，`done` 之后随时可能被驱动重写。

3. **“帧长用 sizeimage”**  
   错。`sizeimage` 是缓冲上界，`bytesused` 才是本帧实际长度。

4. **“REQBUFS 要 4 个就给 4 个”**  
   不一定。驱动可能减少数量，必须检查 `req.count`。

5. **“QBUF 可以重复调用”**  
   同一帧只能还一次；重复还状态就乱了。

6. **“只 close 就行，不用 STREAMOFF/munmap”**  
   不推荐。显式按 STREAMOFF → munmap → close 的顺序释放，状态最清晰。

7. **“S_FMT 设置成功就是我要的格式”**  
   不一定。驱动可能协商成别的格式或尺寸，必须回读确认。

8. **“这个相机可以用 read()”**  
   本机能力位里没有 `READWRITE`，只能用 mmap 流式方式。

## 九、可以动手做的实验

1. **注释掉 `v4l2_capture_done()`**  
   观察：前 4 帧还能出，之后 `DQBUF` 永久阻塞。

2. **把缓冲数改成 2 和 8**  
   观察启动延迟、帧率稳定性、CPU 占用的变化。

3. **把 `CAM_W/CAM_H` 改成 640×480**  
   观察窗口尺寸、帧率和 CPU 的变化。

4. **把 `S_FMT` 的像素格式改成 YUYV**  
   观察回读校验如何让程序直接失败（本程序写死 MJPG）。

5. **在 `get` 前后打时间戳**  
   测量 `DQBUF` 的阻塞时间，和 `[stats]` 的帧率对照。
